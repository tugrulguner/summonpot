This page specifies the public declaration vocabulary and the currently enforced runtime slice. The [capability guide](https://github.com/tugrulguner/summonpot/blob/main/docs/declarative-capabilities.md) remains the detailed canonical source for value-transfer and structural-validation details; this reference maps the common public contract and links to that implementation-focused document.

## Endpoint declaration

`Summon(name)` creates an application registry. `@summon(path, method="POST", model=None)` registers a declaration. The decorated function takes the request contract (a Pydantic model for body endpoints) plus declaration-only dependency markers and returns the endpoint output type. Its docstring is the fixed goal. The body is not executed; call the generated HTTP route, not the Python declaration.

The generated FastAPI app exposes request/response schemas and OpenAPI. POST/PUT/PATCH use request bodies; GET/DELETE/HEAD parameters are query parameters. The supported methods are GET, POST, PUT, PATCH, DELETE, and HEAD. A route's dependency parameters are not client-provided body fields. For example, declare a body route with `@summon("/items", method="POST")` and a query route with `@summon("/items", method="GET")`; parameters on that GET declaration are query inputs. Path placeholders such as `@summon("/items/{item_id}")` must match a declared scalar parameter. The generated API describes these transport fields; they do not create extra capability authority. See [HTTP and error reference](https://github.com/tugrulguner/summonpot/blob/main/docs/declarative-capabilities.md#what-the-boundary-does-and-does-not-cover).

A request model is the body contract; use scalar/list query-compatible parameters for bodyless methods. Dependency-marker parameters such as `result=Required(...)` are declaration-only and excluded from HTTP input schemas. The complete guide examples use POST JSON and can be exercised against `TestClient(build_app(summon))`; for a multi-file CLI-launched app and its acceptance tests, see the [support-service example](https://github.com/tugrulguner/summonpot/tree/main/examples/06_support_service), [example test suite](https://github.com/tugrulguner/summonpot/blob/main/tests/test_examples.py), and [example guide](https://github.com/tugrulguner/summonpot/blob/main/examples/README.md).

## Dependency markers and bounds

| Public call | Meaning | Default bound |
|---|---|---|
| `Depends(operation)` | Expose an optional operation; success need not call it. | zero or more |
| `Required(operation)` | Expose an operation; successful output requires its completion. | at least one |
| `Exactly(n)` | Bound operation starts to exactly `n`. | minimum and maximum `n` |
| `AtLeast(n)` | Require at least `n` calls. | no maximum |
| `AtMost(n)` | Permit up to `n` calls. | minimum zero |
| `Between(minimum, maximum)` | Bound calls to the inclusive interval. | given interval |

`Required(op, calls=AtMost(3))` means at least one and at most three, because `Required` retains its lower bound. `Depends(op, calls=Exactly(1))` is contradictory and rejected; use `Required`. Bounds must be nonnegative built-in integers (a bool is not accepted as an integer count); an upper bound below a lower bound is rejected. For the no-model path specifically, the only admitted marker is one required `Exactly(1)` operation.

Bare callable `Depends(fn)` and `Required(fn)` preserve the legacy agent-backed path. A bare callable does not provide the typed argument-source and operation-output contract of `Operation`.

## Typed operation declaration

```python
operation = Operation(
    callable,
    bind={"argument": FromRequest("field")},
    output=ResultModel,
)
```

This is signature notation rather than a runnable fragment: `callable` and `ResultModel` are placeholders. Use the complete programs in the two Build guides to copy an executable endpoint.

- The first argument is the exact application callable.
- `bind` maps callable parameter names to explicit sources. Missing, extra, incompatible, or unsupported explicit sources fail during endpoint registration.
- `output` declares the operation result schema. In the bound runtime it is locally validated before successful completion; a validation error is not retried automatically.
- The sequential chain introduced in 0.11.0 is two or more required `Exactly(1)` operations linked A→B by `FromResult` or `after`, using `FromRequest`/`FromResult`, immutable defaults, and optionally producer-backed `AgentChoice(from_result=...)` from `list[ConcreteModel]`. It has no context in the historical 0.11.0 behavior or broader bounds. Its v0.11.0 execution is agent-mediated; from 0.12.0 the eligible fully resolved slice runs model-free as described below. The unique terminal output annotation must exactly match the endpoint response annotation; the validated canonical terminal result is returned. `FromResult` establishes readiness; optional `after` adds success-ordering. Canonical result objects stay hidden; tool results are completion acknowledgments, while choice arguments disclose bounded inert candidate evidence. Unsupported graphs fail closed. This behavior is included from 0.11.0; historical v0.10.0 does not include it. Fully resolved uniquely ordered chains with a Pydantic request, at least one `FromRequest` binding, only `FromRequest`/`FromResult` or supported immutable defaults, and the terminal operation's exact full endpoint response annotation execute model-free from version 0.12.0. An `AgentChoice` normally keeps the chain agent-mediated; the result-dependent source exception included from version 0.14.0 is described below. Published v0.11.0 chains remain agent-mediated.
- An `Operation` object is immutable at the declaration boundary: binding mappings are snapshotted and `after` is tuple-normalized.

### Binding sources

| Source | Value authority | Current meaning |
|---|---|---|
| `FromRequest("field")` | Validated request | Canonical request value injected by framework; hidden from agent argument schema. |
| `AgentChoice()` | Agent/model | The specific argument remains model supplied in the supported agent-backed bound-operation slice. |
| `FromResult(operation, "field")` | Validated producer result | Supported for the uniquely ordered sequential chain; result-dependent choice behavior is included from version 0.14.0 and narrowly documented below. |
| `FromContext("key")` | Authenticated application context | Included from version 0.13.0 in the narrow slice described below. |

`FromRequest` values are checked against the receiving callable parameter noncoercively before application code begins. This is data validation, not authentication or authorization. For supported bounds and receiver schema edge cases, consult the [detailed capability contract](https://github.com/tugrulguner/summonpot/blob/main/docs/declarative-capabilities.md#arguments-are-constrained-for-the-first-bound-runtime-slice).

### Explicit shapes accepted today

From 0.12.0, fully resolved uniquely ordered chains of required `Exactly(1)` operations with a Pydantic request, at least one `FromRequest` binding, only `FromRequest`/`FromResult` bindings or supported immutable defaults, and the exact full terminal response annotation run model-free. An `AgentChoice` normally keeps the chain agent-mediated; the result-dependent source exception included from version 0.14.0 is documented in [Result-dependent source choice](#result-dependent-source-choice-included-from-version-0140). Historical published boundaries remain unchanged. The runtime enforces the single-operation contract and, from 0.11.0, sequential result chains with exactly one ready operation at each step. The chain requires two or more required `Exactly(1)` operations, A→B `FromResult` or independent `after` ordering, and `FromRequest`/`FromResult`, supported immutable defaults, or producer-backed `AgentChoice(from_result=...)` from `list[ConcreteModel]`. Authenticated context is supported from version 0.13.0 only in the narrow source slice; broader bounds remain unsupported. An `AgentChoice` normally keeps execution agent-mediated; see the result-dependent source exception included from version 0.14.0 below. Eligible fully resolved chains run model-free from 0.12.0. Its unique terminal output annotation must exactly match the endpoint response annotation, and its validated canonical result is returned. `FromResult` establishes readiness; optional `after` adds success-ordering. Canonical result objects remain hidden; choice arguments disclose bounded inert candidate evidence separately from completion acknowledgments. Unsupported graphs fail registration.

Immutable defaults are exact built-in `None`, `bool`, `int`, `float`, `complex`, `str`, `bytes`; tuples/frozensets recursively containing only these values are also supported. Mutable defaults, custom types/subclasses, and scalar request declarations do not qualify for direct execution.

| Shape | Current execution |
|---|---|
| Complete sole required operation meeting every direct predicate | Runs the operation directly; no model resolution/construction/call. |
| Admitted sole operation or uniquely ordered required `Exactly(1)` chain with authenticated `FromContext` (from 0.13.0), a Pydantic request, at least one `FromRequest`, all remaining inputs resolved through supported bindings/immutable defaults, and exact full terminal response annotation | Model-free execution after authentication and all context receiving checks, provided no `AgentChoice` remains. |
| Otherwise admitted context-only or scalar-request declaration | Agent-mediated; authenticated context does not remove the Pydantic request and `FromRequest` direct-eligibility requirements. |
| Complete sole required operation with a direct `AgentChoice` | Agent-backed runtime; only declared choice values are model supplied. |
| Bare legacy callable dependency | Existing provider-neutral agent path. |
| Unsupported/incomplete explicit `Operation` contract | Rejected during registration. |
| Fully resolved sequential chain meeting every 0.12.0 predicate above | Model-free sequential execution; canonical terminal result returned. |
| Supported sequential chain with producer-backed `AgentChoice` | From version 0.14.0: exactly one eligible choice gets local singleton execution; multiple candidates use lazy model handoff. Historical v0.13.0 chains remain agent-mediated. |
| Unsupported graph or explicit contract | Rejected during registration. |

No runtime fallback to a model occurs after direct execution begins. One reserved start is not exactly-once completion: failures and side effects are application concerns.

## Output and error behavior

Operation output validation occurs before the call counts as successful for `Required`. Endpoint output is validated against its declared response model. For legacy and single-operation agent synthesis, these schema/type guarantees do not prove that model prose derives from operation output. The supported chain instead returns the canonical terminal result. Provider calls may fail or exceed usage limits; HTTP maps invalid request/injected values to 422, usage limits to 429, timeout to 504, and upstream provider errors to 429 (provider throttling) or 502. Public error text is intentionally fixed/redacted; normal server logs omit exception details and capability data. Exact error mapping is implemented in [`server.py`](https://github.com/tugrulguner/summonpot/blob/main/src/summonpot/server.py).

## Security and side effects

Capabilities are real application callables, not simulations. Keep the declared set minimal, validate identity/authorization inside every operation, avoid raw database connections/sessions, shells, arbitrary SQL, and broad service objects, and add application-side idempotency/transaction safeguards where side effects need them. `SUMMONPOT_MODEL=test` is keyless but can invoke capabilities with placeholder arguments: it is not a dry-run sandbox. See [Architecture & safety](/architecture/) and [the agent-backed build guide](/build/agent-choice/).

## Producer-backed choices in sequential chains

Version 0.11.0 supports `AgentChoice(from_result=producer)` only in the uniquely ready
sequential chain, with a declared producer output of `list[ConcreteModel]`. Candidate
projection is inert and bounded (128 items and 65,536 JSON characters per binding), respects
field exclusions and aliases, and invokes no application serializers; the
model receives opaque request-local tokens, not canonical objects or full canonical-result
context. Local token membership maps the selected token to the exact canonical validated
member—Python equality is not authority. Empty, unavailable, or oversized sets produce a
fixed redacted 409 before model decision and before downstream work, with no extra model
request. At the historical v0.11.0 and v0.13.0 boundaries, this remains agent-mediated; from version 0.14.0, the eligible singleton route is local while two or more candidates remain agent-mediated. Direct
single-operation `AgentChoice` remains unchanged.

## Result-dependent source choice (included from version 0.14.0)

Version 0.14.0 adds a narrowly admitted exception to the historical rule that `AgentChoice` keeps a chain agent-mediated. This behavior is included from version 0.14.0; historical published 0.13.0 behavior does not include it. The complete eligible chain must contain exactly one `AgentChoice(from_result=producer)` argument and no other unresolved choice. Its producer declares `output=list[ConcreteModel]`. All other arguments resolve through supported request/result/authenticated-context bindings or immutable defaults. The existing unique-readiness, Pydantic request, at-least-one-`FromRequest`, and exact full terminal response annotation requirements remain.

The framework executes the resolved prefix and checks the candidate domain using the existing inert projection, receiving predicates, and 128-candidate/65,536-character limits, even for singleton domains. No candidates, unavailable evidence, or exceeded limits produce the existing redacted HTTP 409 before model resolution or downstream effects. A singleton is bound to the exact canonical validated member locally; the suffix and canonical terminal response complete without resolving or constructing a model.

Two or more candidates trigger lazy model resolution at the choice boundary. Only bounded inert evidence and opaque request-local tokens are exposed; token membership is checked locally. The suffix remains agent-mediated in that same run, retaining authenticated context, request, results, reservations, stable tokens, and absolute deadline. The prefix is never replayed and model history is not fabricated. Prefix effects can precede a provider-configuration failure; there is no rollback guarantee.

Other supported declarations outside this optimization retain their existing path. Direct single-operation `AgentChoice`, published v0.13.0 behavior, and existing model-free paths are unchanged. Multiple choice points, broader graphs, and repeated calls are not enabled by this optimization.

## Planned vocabulary

`FromContext` outside the narrow supported slice, primitive or untyped collection choices, direct unbounded choices inside chains, broader call bounds, broader graph shapes, and deterministic compilation beyond the supported sequential slice remain unsupported. `FromResult`, `after`, and producer-backed choices work only in the uniquely ordered sequential chain described above. Eligible fully resolved chains run model-free from 0.12.0; any `AgentChoice` normally remains agent-mediated; see the result-dependent source exception included from version 0.14.0 above. Started, failed, or uncertain operations are not replayed in the same run, but this is not rollback or exactly-once external effects.


## Authenticated application context (included from version 0.13.0)

Version 0.13.0 admits `FromContext` only for a single required operation with `Exactly(1)` and an eligible uniquely ordered required `Exactly(1)` chain. This was not included in version 0.12.0. Register `Summon(context=authenticate)` with a sync or async one-request-argument function returning a Pydantic principal configured `frozen=True, extra="forbid"`. Fields must be immutable primitive values or typed tuples/frozensets. `FromContext("tenant_id")` refers to the canonical field name, not its validation alias.

The provider executes anew for each HTTP request inside `Runtime.timeout`, before operations and model resolution. Authentication denial yields a fixed 401; unexpected provider/invalid principal failures yield fixed redacted 500 responses. Context values are not implicitly added to model inputs. Request JSON is not authority. Raw `Runtime.call(..., context=principal)` is a trusted application entry point only. This feature does not implement login, credential policy, operation authorization, or tenant-scoped data access; the application must perform all of those.
The framework does not insert the context object or its values into model instructions, request prompts, schemas, or error responses. This is not a guarantee that a value is secret if application code discloses it: operation outputs may intentionally be returned to the model on the existing single-operation agent path, and that disclosure remains the application's responsibility. FastAPI transport validation occurs before the provider; provider execution is within `Runtime.timeout`. `PermissionError` maps to 401 only when raised by the context provider; an operation's `PermissionError` is an application failure (500).

Principal admission is a non-transforming structural predicate over the authenticator's
canonical values. Validation hooks, custom initialization/post-init hooks, and transforming
model configurations fail registration rather than being replayed to change identity.
