Summonpot modernizes APIs for AI without replacing the endpoint with a separate agent layer. Declare one typed endpoint contract: what callers may send, the fixed goal, the exact application-owned operations Summonpot may orchestrate, and what the endpoint may return.

The agent's authority is bounded by the endpoint declaration. Exact application behavior stays application-owned; semantic choices are agent-owned only where the contract explicitly allows them.

## Try a complete endpoint

This endpoint takes a validated topic, lets the agent choose the operation's response
style, and requires one application-owned operation. The operation computes a candidate
summary; the model cannot supply its topic or replace its implementation. The final
model response is schema-validated, not automatically bound to that candidate.

```python
from typing import Literal

from pydantic import BaseModel, Field
from summonpot import AgentChoice, Exactly, FromRequest, Operation, Required, Summon


class SummaryRequest(BaseModel):
    topic: str = Field(min_length=1, max_length=200)


class SummaryResponse(BaseModel):
    summary: str
    style: Literal["brief", "detailed"]


def build_summary(topic: str, style: Literal["brief", "detailed"]) -> SummaryResponse:
    """Build a summary for the requested topic in the selected style."""
    length = 80 if style == "brief" else 240
    return SummaryResponse(summary=f"{topic[:length]}", style=style)


summary_operation = Operation(
    build_summary,
    bind={"topic": FromRequest("topic"), "style": AgentChoice()},
    output=SummaryResponse,
)

summon = Summon("summary-api")


@summon("/summarize")
def summarize(
    request: SummaryRequest,
    result=Required(summary_operation, calls=Exactly(1)),
) -> SummaryResponse:
    """Summarize the requested topic and choose a brief or detailed style."""
    ...
```

Save as `app.py`, install the serving extras, then start the local API:

```bash
python -m pip install 'summonpot[serve,cli]'
export SUMMONPOT_MODEL=test
summonpot serve app.py --host 127.0.0.1 --port 8000
```

The test model is keyless, **not** a side-effect-free sandbox. This example's operation is
harmless; use only harmless capabilities when wiring your own endpoint. Try it through the
same HTTP route clients use:

```bash
curl -X POST http://127.0.0.1:8000/summarize \
  -H 'Content-Type: application/json' \
  -d '{"topic":"Contract-first APIs keep application behavior explicit."}'
```

This contract requires one `Exactly(1)` operation and declares an `AgentChoice`, so the
operation's call count and the final response schema are enforced. The topic argument is
application-bound; the agent chooses the operation's style argument. The keyless test
model returns placeholder response strings, not a useful semantic summary. Response
validation does not prove that final text reproduces the operation's result.

A fully application-bound operation in the supported single-operation shape can instead
execute directly without resolving a model. A uniquely ordered sequential result chain is included from version 0.11.0 and remains agent-mediated at that boundary. From version 0.12.0, fully resolved chains execute model-free only for a Pydantic request, at least one `FromRequest` binding, a unique required `Exactly(1)` sequence, supported request/result bindings or immutable defaults, and an exact full terminal response annotation. An `AgentChoice` normally remains agent-mediated; the result-dependent source exception included from version 0.14.0 is specified in the [operation reference](/reference/operations/#result-dependent-source-choice-included-from-version-0140). Broader graph execution remains planned. Historical v0.11.0 chains remain agent-mediated; see the [roadmap](https://github.com/tugrulguner/summonpot/blob/main/ROADMAP.md).

The v0.14.0 release supports exactly one producer-backed choice in an otherwise eligible uniquely ordered required `Exactly(1)` chain. Current source (unreleased) supports one or more producer-backed choices with framework-owned progression. In an otherwise eligible uniquely ordered required `Exactly(1)` chain, a Pydantic request, at least one `FromRequest`, supported request/result/authenticated-context bindings or immutable defaults, and exact full terminal response annotation identity remain required. All current consumer domains are checked before selection or start. Singleton bindings resolve locally; a decision-only selector returns ambiguous tokens with no business-operation tools. The shared kernel validates and invokes the operation, then continues locally until another genuine decision is needed. The canonical terminal result returns without a final model acknowledgment. Request/principal, reservations, token domains, usage budgets and one deadline remain request-local across frontiers and corrections. Explicit `tool_calls_limit` retains the previous one-way agent suffix; `allow_direct=False` and other noneligible declarations retain their existing route. Limits remain 128 candidates and 65,536 evidence characters per binding, not an aggregate prompt/context budget. Prefix effects may precede provider-configuration failure; no rollback, effect replay or durable resume is added. Historical v0.13.0 behavior remains agent-mediated for producer-backed choices. Historical v0.14.0 remains exactly-one-choice. See the [operation reference](/reference/operations/) for details.

## Current-source bounded repeated calls (unreleased)

One required typed operation may run a finite positive number of times (`1 <= minimum <= maximum`, `maximum > 1`) with a Pydantic request, at least one `FromRequest`, direct closed `Literal[str]` `AgentChoice` inputs, supported request/context bindings or immutable defaults, and exact full operation-output/endpoint-response annotation identity. Summonpot owns sequential decisions; business functions are not selector tools. It locally validates selections, shares one usage budget and deadline, resolves the model lazily, auto-finishes at maximum, and returns only the final successful canonical result; any failure aborts. Previous-result evidence is limited to 65,536 characters per decision, not an aggregate prompt budget. Explicit `tool_calls_limit` fails before provider/effects. No producer choices, `FromResult`, `after`, zero-minimum/unbounded bounds, implicit batch, or general graph. Existing Exactly(1) and producer-choice routes remain unchanged. Published v0.14.0 is untouched; milestone 3 remains partial and repeated-result addressing in chains remains next. See the [canonical contract](/reference/operations/).

## Shipped today

- Typed contract-first endpoints and generated HTTP/OpenAPI contracts.
- Closed sets of application-owned callables; optional or required operations.
- Bounded agent runtime with locally validated response models and limits.
- A narrow, fully resolved single `Exactly(1)` operation path that executes without resolving or constructing a model.
- Application-authenticated `FromContext` from version 0.13.0, injected from immutable server-created identity before effects, with no caller/model override. See the [context contract](/reference/operations/#authenticated-application-context-included-from-version-0130).
- Fixed, redacted failure responses and logs, with distinct input, operation/model output, provider, usage, application, and timeout categories.
- One monotonic runtime deadline across preparation, execution, and finalization, checked before application effects.

The v0.10.0 deadline excludes HTTP body parsing, request validation, and response serialization. Synchronous work cannot be forcibly stopped, so an operation already running at timeout may still complete its effect. Direct execution does not fall back to a model after it starts. See [failure responses and runtime deadline](/guides/operations/#failure-responses-and-runtime-deadline) for status mappings and application-owned idempotency responsibilities.

Version 0.11.0 sequential chains of two or more required operations with exactly one ready operation at each step were agent-mediated. Fully resolved chains meeting the 0.12.0 boundary above run model-free. Within a chain, `AgentChoice(from_result=producer)` can select from a producer's validated `list[ConcreteModel]` using inert projected descriptions and opaque request-local tokens (at most 128 candidates and 65,536 JSON characters per binding). The selected token maps locally to the exact canonical member; Python equality is not authority. Empty, unavailable, or oversized sets fail with a fixed redacted 409 before model decision or downstream work, without an extra model request. Primitive/untyped collections, direct unbounded choices within chains, broader bounds, and general graph execution remain unsupported. Authenticated context has a narrow implementation included from version 0.13.0, not included in version 0.12.0. Direct single-operation `AgentChoice` is unchanged. This behavior is included from 0.11.0; historical v0.10.0 does not include it. See the [project roadmap](https://github.com/tugrulguner/summonpot/blob/main/ROADMAP.md) and [changelog](https://github.com/tugrulguner/summonpot/blob/main/CHANGELOG.md) for current boundaries.
